Bezpečnost Kubernetes (k3s)

Z části A víme: izolace jednoho kontejneru nestačí. Útok nepřišel přes aplikaci, ale přes vystavený control-plane. U Kubernetes to platí na dvou vrstvách.

Zabezpečený deployment na k3s · RBAC · Secrets · NetworkPolicy · Pod Security · obě vrstvy obrany

Ovládání: → / mezerník vpřed · ← zpět · F celá obrazovka · modré odznaky = číslo skriptu k ukázce (k8s/scripts/)

Návaznost na část A — TeamTNT proč vznikla část B

V A jsme uzavřeli: hardening jednoho kontejneru útok TeamTNT nezastaví, protože útočník nejde přes aplikaci — jde přes vystavený control-plane (Docker API / socket na hostiteli).

Co ukázalo A

  • TeamTNT skenoval vystavené Docker API (TCP 2375)
  • přes API spustil vlastní --privileged kontejner s -v /:/host → root na hostiteli
  • vstup nebyl bug v appce, ale otevřený control-plane

Obrana A: nevystavovat API, rootless / userns-remap.

Co přidává B — dvě vrstvy

  • Kubernetes vrstva (k3s): RBAC, SA, Secrets, NetworkPolicy, Pod Security, image, limity
  • Vrstva hostitele/runtime (Docker na worker nodu): i perfektní RBAC/PSA je k ničemu, když node vystavuje Docker API

Zaměření B: primárně obrana + ověření, že dřívější postup selže.

Teze celé části B: Kubernetes je nutné bránit na obou vrstvách — K8s hardening sám o sobě nestačí bez hardeningu hostitele.

Topologie laboratoře 2 VM · izolovaná síť

Dvě VM v izolované laboratorní síti. VM2 je Docker host z projektu A, nyní připojený jako k3s agent s Docker runtime.

VM1 · k3s-server
control-plane + workload, datastore (sqlite/etcd), API :6443
⇄
VM2 · docker-node
k3s agent --docker, pody = Docker kontejnery

Jak se agent připojí

# na VM2 (má Docker z projektu A)
curl -sfL https://get.k3s.io | \
 K3S_URL=https://$K3S_SERVER_IP:6443 \
 K3S_TOKEN=$K3S_TOKEN \
 sh -s - --docker

Žádné hardcoded IP — vše z k8s/scripts/env.sh.

Proč na tom záleží

  • Pody VM2 reálně běží jako Docker kontejnery (embedded cri-dockerd, k3s 1.24+)
  • Kdo ovládne Docker na VM2, ovládne pody mimo dohled Kubernetes
  • Přesně to spojuje B zpět na TeamTNT z A

Proč k3s lehký, ale plnohodnotný

k3s = jednobinární Kubernetes (SUSE/Rancher). Rychlá instalace jedním skriptem, embedded datastore. Bezpečnostní modely jsou identické s plným Kubernetes, takže demonstrace je plně přenositelná.

Lehký do laboratoře

Jeden binary, nízké nároky, ideální na VM. curl -sfL https://get.k3s.io | sh.

Stejné mechanismy

RBAC, PSA, NetworkPolicy, Secrets — stejné API i chování jako „velký" K8s.

Baterie uvnitř

flannel + kube-router (NetworkPolicy funguje out-of-the-box), admission PodSecurity + NodeRestriction (1.25+).

Pozor na jedno: --secrets-encryption se zapíná jen při prvním startu serveru (vygeneruje AES klíč). Dodatečně nelze — insecure cluster startuje bez něj, secure s ním.

Mapa útočné plochy Kubernetes

Tři vrstvy, kde se chybná konfigurace projeví. Část B pokrývá všechny tři — včetně té, kterou RBAC/PSA neřeší.

Control-plane

API server (:6443), kubelet, datastore (etcd/sqlite). Anonymní přístup, nešifrovaný datastore, slabý RBAC.

Workload

Pody, ServiceAccount tokeny (automount), Secrets v ENV, privileged/hostPath, žádné limity, plochá síť.

Node / runtime

Docker na VM2. Vystavené API 2375 = převzetí nodu mimo K8s. Sem RBAC/PSA nedosáhnou.

Reálné kampaně: TeamTNT a Hildegard cílily přesně na špatně zabezpečené Kubernetes/Docker API a SA tokeny — miner a laterální pohyb po převzetí nodu. B ukazuje obranu každé vrstvy.

RBAC & ServiceAccount skript 01/05

Scénář: NEBEZPEČNÉ cluster-admin + automount → HARDENED minimální Role

NEBEZPEČNÉ — SA = cluster-admin

# insecure/02-rbac-overprivileged.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  namespace: insecure-demo
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding      # platí v CELÉM clusteru
metadata:
  name: app-sa-cluster-admin
subjects:
  - kind: ServiceAccount
    name: app-sa
    namespace: insecure-demo
roleRef:
  kind: ClusterRole
  name: cluster-admin         # ← VŠECHNA práva
  apiGroup: rbac.authorization.k8s.io
# 01-workload.yaml → spec.serviceAccountName: app-sa
# automount nenastaveno → default true → token JE v podu

HARDENED — least privilege

# secure/02-rbac-minimal.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: safeapp-sa
  namespace: secure-demo
automountServiceAccountToken: false   # token NENÍ v podu
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role                       # platí JEN v namespace
metadata:
  name: safeapp-minimal
  namespace: secure-demo
rules:
  - apiGroups: [""]
    resources: ["configmaps"]      # žádné secrets!
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding                # LEPIDLO: SA ↔ Role
metadata:
  name: safeapp-minimal
subjects:
  - kind: ServiceAccount
    name: safeapp-sa            # ← odkaz na SA výše
roleRef:
  kind: Role
  name: safeapp-minimal         # ← odkaz na Role výše
  apiGroup: rbac.authorization.k8s.io

Secrets skript 02/06

Scénář: NEBEZPEČNÉ ENV + nešifrovaný datastore → HARDENED soubor + šifrování

NEBEZPEČNÉ — ENV + plaintext

# insecure/03-secret-plaintext.yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
  namespace: insecure-demo
type: Opaque
stringData:                     # v datastore jen base64, NE šifra
  DB_PASSWORD: "S3cr3t-DB-Heslo-FAKE"
# 01-workload.yaml → secret jako ENV:
envFrom:
  - secretRef: {name: app-secrets}

HARDENED — soubor + do datastore + encryption

# secret NE z manifestu se stringData (plaintext v Gitu),
# ale imperativně → rovnou do datastore přes API server:
kubectl create secret generic safeapp-secrets \
  -n secure-demo \
  --from-env-file=secrets.env      # z trezoru/CI, ne z Gitu
# idempotentně: … --dry-run=client -o yaml | kubectl apply -f -
# v produkci zdroj = Vault / ExternalSecrets / SealedSecrets
# secure/01-workload.yaml → mount jako SOUBOR, ne ENV:
volumeMounts:
  - {name: secrets, mountPath: /run/secrets, readOnly: true}
volumes:
  - name: secrets
    secret: {secretName: safeapp-secrets, defaultMode: 0440}

ENV — úniky i BEZ kódu v kontejneru

  • docker inspect → .Config.Env (přes Docker API, bez exec)
  • dědí child procesy → logy, crash-dumpy, debug endpointy
  • /proc/<pid>/environ + config kontejneru na disku nodu
  • zůstává v prostředí po celý běh procesu

Soubor — jen aktivní čtení ve správném kontextu

  • NENÍ v inspect ani v env
  • nedědí child procesy, neleaká do logů
  • čte jen vlastník/fsGroup (0440), read-only, tmpfs (RAM)
  • vyžaduje být v kontejneru (RCE) nebo mít host/Docker API
Soubor není všespásný: útočník s shellem jako app-user (RCE) nebo s přístupem k hostiteli / Docker API 2375 secret stejně přečte (cat /run/secrets/…). Mount jen odřízne pasivní a vzdálené cesty a minimální RBAC zmenší kořist (jen vlastní secret, ne celý cluster). Skutečná obrana = krátké TTL / workload identity, zabránit RCE (Pod Security, slide 9) a zavřít Docker API (slide 12).
--secrets-encryption musí být nastaveno při prvním startu serveru — vygeneruje AES-CBC klíč do encryption-config.json. Zapnout dodatečně nejde.

NetworkPolicy skript 03/07

Scénář: NEBEZPEČNÉ plochá síť → HARDENED default-deny

NEBEZPEČNÉ — bez policy

Bez NetworkPolicy je provoz plochý: pod↔pod napříč namespaces, volný egress ven.

# z podu v insecure-demo:
curl http://victim.secure-demo # PROJDE
curl http://evil-c2.example      # egress volný
# → prostor pro laterální pohyb a C2

HARDENED — default-deny + cílené

# deny vše, pak povolit jen nutné
policyTypes: [Ingress, Egress]
# povoleno: frontend→backend, DNS

Vynucuje kube-router. Ostatní toky selžou:

curl http://victim.secure-demo
# timeout → BLOKOVÁNO

Segmentace (frontend / backend / db) brání laterálnímu pohybu i exfiltraci — povolen jen tok, který appka reálně potřebuje, plus DNS na kube-dns.

Pod Security Admission skript 08

Scénář: NEBEZPEČNÉ privileged/root/hostPath → HARDENED PSA restricted

NEBEZPEČNÉ — namespace bez PSA

Namespace bez labelu povolí privileged pod, runAsUser: 0, hostPath: /.

securityContext:
  privileged: true
  runAsUser: 0
volumes: [{hostPath: {path: /}}]
# pod naběhne — FS hostitele v podu

HARDENED — enforce: restricted

# label na namespace
pod-security.kubernetes.io/enforce: restricted

Admission controller privileged pod odmítne už při vytvoření:

kubectl apply -f privileged-pod.yaml
# Error: violates PodSecurity "restricted"
# → BLOKOVÁNO
restricted není default — zapíná se labelem na namespace. safeapp má runAsNonRoot, drop ALL, readOnlyRootFilesystem, seccompProfile: RuntimeDefault → projde.

Image security — Trivy skript 12

Scénář: NEBEZPEČNÉ :latest → HARDENED digest pin + sken

NEBEZPEČNÉ — :latest

Plovoucí tag = neznámý obsah, žádná reprodukovatelnost, tiché záplaty i regrese.

image: myapp:latest

HARDENED — pin na digest

image: myapp@sha256:abc123…

Nezměnitelný obsah + zákaz :latest + sken v CI.

Trivy — dva režimy (z projektu A)

# 1) zranitelnosti v image
trivy image --severity HIGH,CRITICAL myapp@sha256:...
# 2) misconfig sken Kubernetes manifestů
trivy config k8s/manifests/insecure   # privileged, runAsRoot, chybí limity
trivy config k8s/manifests/secure     # čisté

trivy config odhalí špatně nakonfigurované manifesty ještě před nasazením — insecure vs. secure jasně odliší.

Resource limits skript 04/12

Scénář: NEBEZPEČNÉ bez limitů → HARDENED requests/limits + kvóty

NEBEZPEČNÉ — bez limitů

Neškodný busy-loop pod (žádná reálná těžba) zabere CPU celého nodu = DoS efekt.

# pod bez limits:
while true; do :; done
kubectl top pod   # CPU na stropu nodu

HARDENED — limity + kvóty

resources:
  requests: {cpu: 100m, memory: 64Mi}
  limits:   {cpu: 500m, memory: 256Mi}

Navíc LimitRange (default limity) + ResourceQuota na namespace — strop platí i pro zapomenutý pod.

# busy-loop narazí na strop (throttling)
# node zůstane použitelný → BLOKOVÁNO

LimitRange vynutí default limit u podů, které si ho samy nenastaví; ResourceQuota ohraničí celkovou spotřebu namespacu.

Host / Docker runtime skript 09/10 pointa návaznosti na A

Scénář: NEBEZPEČNÉ Docker API 2375 → HARDENED zavřené API + userns-remap

NEBEZPEČNÉ — vystavené API 2375

# útočník přímo na Docker na VM2:
docker -H tcp://docker-node:2375 run \
  -v /:/host alpine \
  head /host/etc/shadow
# root na nodu — mimo Kubernetes
kubectl get pods -A # tento kontejner NEVIDÍ

Přesně vektor TeamTNT z části A. RBAC, PSA, NetworkPolicy sem nedosáhnou — K8s o kontejneru neví.

HARDENED — zavřít control-plane hostitele

  • Docker API nevystavovat — jen unix socket, příp. mTLS na 2376
  • Firewall blokuje 2375 na izolované síti
  • userns-remap — container root ≠ host root
  • no-new-privileges v daemon.json
docker -H tcp://docker-node:2375 ...
# connection refused → BLOKOVÁNO
Pointa celé části B: i dokonalý Kubernetes hardening je k ničemu, když worker node vystavuje Docker API. Obrana musí být na obou vrstvách — přesně jako jsme slíbili v závěru A.

Jaké riziko představuje nesprávná konfigurace Kubernetes?

Shrnutí bezpečnostní analýzy — povinný výstup zadání.

Rizika chybné konfigurace

  • Eskalace práv: přeprivilegovaný SA → z jednoho podu kontrola celého clusteru
  • Únik dat: secrets v ENV a nešifrovaném datastore
  • Laterální pohyb a C2: plochá síť bez NetworkPolicy
  • Útěk z kontejneru: privileged / hostPath / root
  • DoS: pody bez limitů položí node
  • Převzetí nodu: vystavené Docker API mimo dohled K8s

Principy obrany

  • Defense-in-depth přes obě vrstvy: Kubernetes i hostitel/runtime
  • Least privilege: minimální RBAC, drop capabilities, non-root, PSA restricted
  • Default-deny: síť i oprávnění zavřít a otevřít jen nutné
  • Šifrování a sken: secrets-encryption, Trivy image + config
  • Ověřování obrany: po zabezpečení dřívější útok měřitelně selže
Hlavní závěr: Kubernetes hardening sám o sobě nestačí bez hardeningu hostitele. Perfektní RBAC a PSA neochrání cluster, jehož worker node vystavuje Docker API — riziko je nejvyšší právě tam, kde se zabezpečí jen jedna vrstva.
Shrnutí

Bezpečnost na obou vrstvách, ne jen v Kubernetes

Nebezpečné

cluster-admin SA · secrets v ENV · plochá síť · privileged · :latest · bez limitů · vystavené API 2375

Hardened

minimální RBAC · secrets soubor + šifrování · default-deny · PSA restricted · digest pin + Trivy · limity · zavřené API

Least privilege + defense-in-depth přes K8s i hostitele = drtivá většina rizik zmizí.
