Kontejner není virtuální stroj

Všechny kontejnery sdílejí jedno jádro hostitele. Izolace není hardwarová — drží ji jen jaderné mechanismy.

Co drží izolaci

  • namespaces — co kontejner vidí (pid, net, mnt…)
  • cgroups — kolik zdrojů smí
  • capabilities — co smí root uvnitř
  • seccomp / AppArmor — filtr syscallů

Když to vypneme

--privileged, --cap-add, bind-mount /, docker.sock…

„root v kontejneru“ → „root na hostiteli“.

Tři scénáře, které porovnáme

NEBEZPEČNÉ

Privileged

UID 0, --privileged, přístup ke všem /dev, žádné limity.

VÝCHOZÍ

Root (default)

Běží jako root, ~14 capabilities, zapisovatelný FS. „Funguje“, ale děravé.

HARDENED

Least privilege

Non-root, cap-drop=ALL, read-only, limity, izolovaná síť.

Cíl: ukázat dopad (čtení /etc/shadow) a pak ho zavřít.

Chybí CAP_SYS_ADMIN → ani výchozí root sám disk hostitele nepřipojí.

🔴 Privileged — přidá VŠE (~40)

SYS_ADMINSYS_MODULESYS_RAWIO SYS_PTRACEDAC_READ_SEARCHNET_ADMIN SYS_BOOTSYS_TIMEMAC_ADMIN…

+ všechna /dev zařízení + seccomp/AppArmor vypnuté.
SYS_ADMIN = mount → escape (skript 02).

🟢 Hardened — drop=ALL

NET_BIND_SERVICEvšech 14 ostatních

Zahodit vše, vrátit jen nutné (port <1024). Bez SYS_ADMIN → mount selže, escape nefunguje (skript 12).

Rozdíl 🟡→🔴 = ze 14 kontrolovaných oprávnění skok na ~40 + devices + vypnuté bezpečnostní profily.

Starší CVE jako ilustrace řetězení

„Appka v kontejneru má RCE → útočník je uvnitř jako root → díky staré vrstvě escapne na hostitele.“

Co je RCE?

Remote Code Execution — vzdálené spuštění kódu. Útočník přes zranitelnost v aplikaci (injection, nebezpečná deserializace, chybný upload…) donutí službu vykonat vlastní příkazy a získá shell uvnitř kontejneru.

Co je „stará vrstva“?

Docker image = vrstvy (base image + balíčky + appka). Zastaralá vrstva nese známou CVE (starý bash, runc, knihovna), kterou útočník po získání shellu zneužije k escapu. Skenery 10/11 je hledají.

CVE-2019-5736 — runc escape

Přepsání binárky runc z kontejneru → spuštění kódu na hostiteli. Dnes záplatováno; ukázka principu „root uvnitř + stará runtime = escape“.

Shellshock — CVE-2014-6271

Na starém image bash:4.3 stačí jediná proměnná prostředí. Krásně demonstruje „stará vrstva = stará díra“, kterou odhalí scanner.

Volíme záměrně staré, dnes neaktuální zranitelnosti — jsou rychlé a bezpečné na ukázku v laboratoři.

Únik #1 — bind-mount kořene skript 01 /etc/shadow

Scénář: Root (default) → Hardened (obrana)

Útok — žádný exploit

# obyčejný alpine, BEZ --privileged
docker run --rm \
 -v /:/host:ro alpine \
 head /host/etc/shadow

Operátor připojil celý / hostitele → hashe hesel unikly do kontejneru.

Obrana

  • Pojmenované volumes místo bind-mountů
  • Mountovat jen nutnou podsložku, nikdy /
  • Vždy :ro, když stačí čtení
-v app-data:/data:ro

Named volume — vytvoření a výhody

# vytvoření a připojení
docker volume create app-data
docker run -v app-data:/data myapp
# přehled a smazání
docker volume ls
docker volume rm app-data
  • Izolace: spravuje Docker (/var/lib/docker/volumes/…), obsahuje jen data appky — ne soubory hostitele
  • Perzistence: data přežijí smazání i recreaci kontejneru
  • Přenositelnost: jméno místo absolutní cesty → funguje na libovolném hostiteli
  • Konzistentní backup: zálohuje se stejným postupem (pomocný kontejner + tar) bez ohledu na úložiště; drivery umí snapshoty

Jméno bez / = named volume (bezpečné). Cesta s / = bind-mount filesystému hostitele.

Únik #2 — privileged mode skript 02

Scénář: Privileged → Hardened (obrana)

Útok — mount disku hostitele

docker run --privileged alpine
fdisk -l            # vidí disky hostitele
# čte disk přímo, read-only, bez mountu:
debugfs -R "cat /etc/shadow" /dev/sda1

--privileged = všechny capabilities + všechna /dev + vypnuté profily → root na hostiteli.

Místo toho

  • Přidat konkrétní capability nebo device
  • --device=/dev/xyz cíleně
  • Nechat default seccomp/AppArmor zapnutý
# skoro nikdy: --privileged
# správně: --cap-add=NET_ADMIN
Nejčastější důvod? „Nefungovalo to, tak jsme dali --privileged.“ — a tím padla veškerá izolace.

Únik #3 — Docker socket skript 03

Scénář: Root (default) + namountovaný socket → Hardened (obrana)

/var/run/docker.sock = komunikační kanál (API) k Docker démonu. CLI docker jen posílá přes socket příkazy démonu, který běží jako root a skutečně vytváří kontejnery. Kdo dosáhne na socket, ovládá root démon = root na hostiteli.

Útok — kdo má socket, má hostitele

-v /var/run/docker.sock:…
# z kontejneru spustím nový:
docker run -v /:/host alpine \
  head /host/etc/shadow

Přístup k socketu = plná kontrola démona → spustím kontejner s -v / a čtu cokoliv.

Obrana

  • Socket nemountovat (časté u CI, portaineru, monitoringu)
  • Když build nutný → rootless builder (buildkit/kaniko)
  • Nebo socket-proxy s povolením jen čtených endpointů
  • Nikdy do kontejneru dostupného z internetu
Pointa úniků 01–03: není to chyba Dockeru, ale příliš velká oprávnění daná kontejneru.

root vs. non-root skript 04

Scénář: Root (default) → Hardened

Výchozí: UID 0

docker run alpine id
uid=0(root) gid=0(root)

UID 0 uvnitř = UID 0 na hostiteli. RCE → root. Soubory ve volume patří rootovi hostitele.

Non-root (USER 10001)

docker run --user 10001 alpine id
uid=10001 gid=10001

Útočník je „nikdo“. Doplnit --security-opt=no-new-privileges.

V Dockerfile stačí jediný řádek: USER 10001.

⚠ Ani non-root není absolutní — sdílené jádro

Dirty Pipe (CVE-2022-0847) — chyba v Linux jádře (≥ 5.8): neprivilegovaný uživatel mohl přepsat i read-only soubory a povýšit na root. Protože kontejnery sdílejí jádro hostitele, zabírá i zevnitř kontejneru. Veřejné PoC, v katalogu CISA KEV.

Proto non-root není konec, ale jedna vrstva: patchované jádro + cap-drop + seccomp ji zálohují (defense in depth).

Linux capabilities skript 05

Scénář: Root (default) → Hardened

Rozbijí všemocného roota na dílčí oprávnění. Docker dává defaultně ~14; appka obvykle nepotřebuje skoro žádnou.

Výchozí sada

Obsahuje např. CAP_NET_RAW, CAP_CHOWN, CAP_SETUID… zbytečně široké.

Least privilege

--cap-drop=ALL \
--cap-add=NET_BIND_SERVICE

Zahodit vše, přidat jen nutné (port <1024). Zmizí CAP_SYS_ADMIN → mizí mount/escape.

Hmatatelný rozdíl: chown (změna vlastníka) jde jen s CAP_CHOWN — jinak i root dostane „Operation not permitted".

read-only filesystem skript 06

Scénář: Root (default) → Hardened

Zapisovatelný rootfs

Útočník si uloží nástroje, backdoor, zajistí persistenci.

echo malware > /usr/local/bin/x
zápis PROŠEL

Neměnný FS + tmpfs

--read-only \
--tmpfs /tmp:rw,noexec,nosuid

Rootfs zamčený, zápis jen do /tmp v RAM. noexec brání spuštění nahraného souboru.

Omezení zdrojů (cgroups) skript 07

Scénář: Root (default) → Hardened

Bez limitů jeden kontejner (fork bomba, memory leak) položí celý hostitel = DoS.

Paměť

--memory=256m

Nad limit → OOM jen v kontejneru.

CPU

--cpus=0.5

Max 50 % jednoho jádra.

Procesy

--pids-limit=100

Fork bomba narazí na strop.

Demo ukáže měřitelně: 100 procesů narazí na pids-limit (can't fork), paměťový žrout zabije OOM killer (exit 137), stejný výpočet s --cpus=0.2 trvá násobně déle.

Síťová izolace skript 08

Scénář: Root (default) → Hardened

Default bridge

Kontejnery na sebe vidí přes IP → laterální pohyb po kompromitaci.

User-defined net

Segmentace (frontend/backend/db), DNS podle jmen, DB nevystavená ven.

--network none

Kontejner bez sítě, když ji nepotřebuje. Jen loopback.

User-defined síť — vytvoření a výhody

# vytvoření a připojení
docker network create app-net
docker run --network app-net myapp
# přehled a smazání
docker network ls
docker network rm app-net
  • Izolace: kontejnery vidí jen na ty ve stejné síti — jiná síť je nedosažitelná (brání laterálnímu pohybu)
  • DNS podle jmen: kontejnery se najdou podle názvu (http://victim), ne přes křehké IP
  • Segmentace: frontend-net / backend-net / db-net odděleně → DB nikdy vystavená ven
  • Kontrola: explicitní připojení (--network), ne sdílený default bridge, kde na sebe vidí všichni

Default bridge = plochá síť (všichni na všechny). --network none = žádná síť. --network host = nikdy (ruší izolaci).

Secrets skript 09

Scénář: Root (default) → Hardened

Každý zlozvyk uniká jiným kanálem — a „smazání" nepomůže:

❌ ENV proměnná

Uniká přes docker inspect (.Config.Env), /proc/<pid>/environ a logy CI.

❌ COPY/RUN v image

V inspect není — zůstane ve vrstvě i po rm. Odhalí docker history, docker save, Trivy.

✓ Správně

BuildKit --secret (jen při buildu) + za běhu soubor v /run/secrets.

Build-time secret (BuildKit)

# nezůstane ve vrstvě image
RUN --mount=type=secret,id=token npm ci
$ docker build --secret id=token,src=./token .

Runtime secret — /run/secrets

Adresář na tmpfs (v RAM). Orchestrátor (Swarm/K8s) vloží secret jako soubor, read-only, jen do autorizovaných kontejnerů. App ho čte ze souboru → není v inspect, environ, logách ani image; jde rotovat bez rebuildu.

Zlatý standard — vše pohromadě skript 12

Hardened — všechny obrany scénáře pohromadě
docker run -d --name app \
  --user 10001:10001 \                      # non-root
  --read-only --tmpfs /tmp:rw,noexec,nosuid \  # neměnný FS
  --cap-drop=ALL --cap-add=NET_BIND_SERVICE \  # least privilege
  --security-opt=no-new-privileges \          # bez eskalace
  --memory=256m --cpus=0.5 --pids-limit=100 \  # anti-DoS
  --network app-net \                        # izolovaná síť
  -v app-data:/data:rw \                      # pojmenovaný volume
  myapp:pinned-1.2.3                           # pinovaná verze
Skript 12 to spustí a přes docker inspect ověří, že escape z kroku 02 už nefunguje.

Reálný svět — TeamTNT & rootless Docker case study

Útok TeamTNT (reálná skupina)

  • masscan hledá vystavené Docker API (TCP 2375/2376…)
  • přes API si spustí vlastní --privileged kontejner s -v /:/host
  • → root na hostiteli: miner, krádež credentials, rootkit, laterální pohyb
  • malicious image staženo 150 000+×

Vstup NEBYL chyba v appce, ale vystavený control-plane (API/socket). Miner privileged nepotřeboval — sloužil k převzetí hostitele.

Rootless Docker (systémová obrana)

  • Daemon i kontejnery běží pod neprivilegovaným uživatelem
  • Container root → mapované UID → /etc/shadow i host root mimo dosah
  • I --privileged nedá skutečný host root
  • Alternativa pro rootful daemon: userns-remap

Není všelék — kombinovat s nevystaveným API, cap-drop, read-only.

Hlavní ponaučení: nevystavovat Docker API/socket (TLS, firewall na 2375) + rootless / userns-remap → i po průniku útočník nedosáhne na roota hostitele.
Shrnutí

Izolace je volba, ne výchozí stav

Nebezpečné

root · --privileged · bind-mount / · docker.sock · bez limitů · EOL image

Hardened

non-root · cap-drop=ALL · read-only · limity · izolovaná síť · sken + pinování

Princip nejmenších oprávnění + pravidelný sken = drtivá většina rizik zmizí.
